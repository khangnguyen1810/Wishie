# AI Gift Suggestions — Design Spec

**Date:** 2026-07-20
**Branch:** `feature/recommend-gift-for-user`
**Status:** Approved for planning

## Summary

Let a wishlist **owner** generate 5-6 personalized gift ideas for their own wishlist,
based on their selected interests (plus age and a "don't duplicate" list). Each
suggestion is a fully-populated product (name, description, price, product link, image)
that the owner can add to the wishlist with one tap.

Ideas are generated by Google Gemini (free tier) via a Firebase callable Function that
holds the API key server-side. Real product links and images are resolved client-side by
reusing the existing `ProductMetadataService` (WKWebView scraper), with results streamed
into the UI as they validate.

## Goals

- Owner taps "Suggest gifts for me" and receives 5-6 tailored, addable gift cards.
- Each card has: image, name, price, description, and an **Add** button.
- Available from two entry points: the create-wishlist flow and the wishlist detail
  screen — both through the shared `AddItemOptionSheet`.
- No API key in the app binary.

## Non-Goals (YAGNI)

- Suggestions for gift-givers/members (only the owner filling their own list).
- Occasion-based tuning from wishlist name/due date.
- Caching or history of past suggestions.
- Server-side (headless) link scraping.

## Audience & Behavior

- **Audience:** the wishlist owner, filling their own list.
- **Action:** tapping **Add** on a suggestion creates a `WishlistItem` populated with
  name, description, price, `itemLink`, and `image`.
  - In the **create-wishlist flow**, the item is appended to
    `CreateWishlistViewModel.items` (in-memory; persisted when the wishlist is saved).
  - In the **detail screen**, the item is added to the existing Firestore wishlist,
    reusing the current add-item path.

## Idea Source & Architecture

- **Model:** Google Gemini, free tier, JSON-structured output.
- **API architecture:** app → **Firebase callable Function** (`suggestGifts`) → Gemini.
  The Gemini API key lives only in the Function's config. No key ships in the app.
- **Link + image sourcing:** Gemini cannot reliably produce real, working product URLs
  or images. So the Function requests **8-10** ideas (over-request), and the app then
  validates each candidate link **client-side** via `ProductMetadataService`, keeping the
  first **5-6** that resolve to a reachable page with an image.

## Personalization Inputs

- **Interests** (required signal): `UserModel.interests` (hobby ids) mapped to
  human-readable names via `hobbyCategories`.
- **Age:** computed from `UserModel.dateOfBirth`, to bias toward an age-appropriate range.
- **Avoid duplicates:** existing wishlist item names passed to Gemini as a "do not
  suggest" list. In the create flow, uses items added so far.
- **Explicitly excluded:** occasion/event context.

## Pipeline (Approach A — client scrape, progressive reveal)

1. App gathers inputs (interests, age, existing item names).
2. **No-interests gate:** if `interests` is empty, present an interest-picking step first;
   once the owner selects interests, generation continues automatically.
3. App calls `suggestGifts` → Function calls Gemini → returns 8-10 raw ideas
   `{ name, description, price, link }`.
4. Results sheet opens **immediately** in a loading state.
5. App validates candidate links **concurrently** (bounded concurrency, e.g. 3-4 at a
   time) with a **per-link timeout**, via `ProductMetadataService`.
6. Validated suggestions **stream into the sheet** as cards, capped at **5-6**.
7. Owner taps **Add** on any card → a fully-populated `WishlistItem` is added.

## Components

### Server — Firebase Function

- **`suggestGifts`** (callable, Node.js)
  - Input: `{ interests: [String], age: Int?, existingItemNames: [String] }`
  - Output: `{ ideas: [{ name: String, description: String, price: String, link: String }] }`
  - Holds `GEMINI_API_KEY` in Function config/secrets.
  - Builds a structured prompt (interests, age, avoid-list), requests **8-10** ideas with
    JSON output, parses and returns them.
  - On malformed/failed Gemini response: returns an error the app can surface as retry.

### Client — Swift

- **`GiftSuggestionModels.swift`**
  - `GiftIdea` — raw idea from the Function (`name`, `description`, `price`, `link`).
  - `GiftSuggestion` — validated: `GiftIdea` + resolved `ProductMetadata`, ready to display
    and to convert into a `WishlistItem`.
- **`GiftSuggestionService.swift`** — calls the `suggestGifts` callable via the existing
  Firebase SDK; returns `[GiftIdea]`.
- **`GiftSuggestionViewModel.swift`** — orchestrates the pipeline:
  - fetch ideas → validate links concurrently through `ProductMetadataService`
    (bounded concurrency + timeout) → publish `GiftSuggestion`s as they arrive, cap at 6.
  - Handles: empty-interests routing (then resume), errors, and the
    "fewer than ~3 validated" case.
  - Builds a `WishlistItem` from a `GiftSuggestion` on Add.
- **`GiftSuggestionsSheet.swift`** — results sheet: loading placeholders, streamed cards,
  per-card Add, retry action, and the "not enough results / try again" state.
- **`GiftSuggestionCard.swift`** — single card: image, name, price, description, Add button.
- **`AddItemOptionSheet.swift`** (edit) — add a third **"✨ Suggest gifts for me"** row +
  callback, so both entry points reuse it.

## Data Flow & Edge Cases

- **Inputs → prompt:** interest ids → names via `hobbyCategories`; age from
  `dateOfBirth`; existing names as a "do not suggest" list.
- **Over-request & cap:** request 8-10, keep first 6 that validate (reachable link +
  image). If fewer than ~3 validate, show what we have plus a **Try again** action.
- **Concurrency:** validate N links at once (3-4) with per-link timeout so one slow store
  page can't stall the sheet.
- **No interests:** route to interest picker, then resume generation automatically.
- **Errors:** network/Function failure or malformed Gemini JSON → friendly error + retry.
- **Duplicates on Add:** respect the existing "no duplicate item" rule already in the app.
- **Owner-only:** the entry row shows only for owners (create flow = always owner; detail
  flow already gates on `isOwner()`).

## Testing

- **Unit:**
  - Input/prompt builder: interests→names mapping, age calc from `dateOfBirth`, dedupe list.
  - Function response parsing (well-formed and malformed JSON).
  - ViewModel validation pipeline with a **mocked `ProductMetadataService`**: all-success,
    timeout, partial failures, and `<3` validated results.
  - Add → `WishlistItem` mapping (all fields populated correctly).
- **Function:** local test for prompt construction and Gemini response parsing (mocked HTTP).

## Prerequisites / Setup (called out for the plan)

- Firebase **Blaze (pay-as-you-go)** plan enabled (required to deploy callable Functions
  and make outbound calls to Gemini).
- A **Gemini API key** created and stored in the Function's config/secrets
  (not in the app).
- Firebase Functions tooling initialized in the repo if not already present.

## Reference — Existing Types

- `WishlistItem`: `id, name, description, image?, pickedUserId?, isPicked, isMostDesired,
  localImage?, itemLink, price?`.
- `ProductMetadata`: `title, productDescription, imageUrl?, productUrl, price?`.
- `UserModel`: `... dateOfBirth, interests: [String], hasCompletedInterestsSetup`.
- `hobbyCategories`: interest id → `{ name, emoji }` catalog.
- `ProductMetadataService.fetchMetadata(from:)`: WKWebView scraper returning
  `ProductMetadata`.
- `AddItemOptionSheet`: shared add-item entry, used by create flow and detail screen.
